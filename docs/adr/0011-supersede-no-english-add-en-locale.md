# Add English (`en`) as a Third Locale — Supersede ADR-0007

The site now supports three Locales: Arabic (`ar`, RTL), French (`fr`, LTR), and English (`en`, LTR). ADR-0007 ("Two-Locale Ceiling — No English") is consciously superseded by this ADR. The sponsor's audience now includes anglophone international press and partners who require an English surface to navigate the Profile at all; French alone is no longer sufficient.

## Decision

- The closed `LocaleCode` union is widened from `"ar" | "fr"` to `"ar" | "fr" | "en"`. `LOCALE_META` gains an `en` entry (`{ name: "English", dir: "ltr", htmlLang: "en" }`). `DEFAULT_LOCALE` remains `"ar"` — the home audience is still Chad and the Arab world; English and French are the artefacts of international reach.
- Every Content Item table gains paired `*_en` columns alongside `*_ar` and `*_fr`: `title_en`, `body_en`, `degree_en`, `institution_en`, `honours_en`, `venue_en`, `caption_en`, `category_en`, `photographer_credit_en`, `role_other_en`, `published_in_name_en`, `tagline_en`.
- The shared publish-gate validator `validate_content_item_publish` is widened to take `title_en_in` and `body_en_in` and require all three Locales to be non-empty when `status = 'published'`. Every per-table trigger that calls the validator is widened to pass the new arguments. Per-table triggers that enforce paired fields (`institution`, `venue`, `role_other`, etc.) gain the symmetric `_en` rule.
- The locale switcher lists all three Locales. The language detector reads `Accept-Language` on the `/` root route and redirects to the best-matching Locale segment (`/ar`, `/fr`, or `/en`) when no Locale segment is present (the existing matcher stays scoped to `/portal/*`; the detector lives in the root `page.tsx` via `headers()` so the middleware pattern is unchanged in shape).
- `hreflang` alternates on every public page render all three Locales. `<html lang>` is set to `ar` | `fr` | `en` by the existing `LocaleDocumentDirector` based on the first path segment.
- Inline per-Locale ternaries throughout public pages are widened to a third branch via the new `textFor(locale, { ar, fr, en })` helper exported from `@/lib/i18n/locales`. Records (`ABOUT_COPY`, `NAVIGATION_LABELS`, `STRINGS`, `ROLE_LABELS`) gain an `en` block.

## Considered Options

- **English optional / fall back to French** (the original draft of this ADR's first proposal). Rejected: asymmetric-publication risks that ADR-0003 was written to prevent would re-emerge for the ar↔fr pair under a new ar/fr↔en pair; an English reader landing on an article whose English body wasn't yet written would see French text mixed with English chrome — a credibility risk that ADR-0003's symmetric-publish rule was specifically designed to make impossible.
- **Chrome-only localization** (nav/footer/CTAs in English; Content Items stay paired ar/fr and the `/en/` page renders the French Content Item with English chrome). Rejected by the sponsor because it produces a visibly broken English experience — the very thing this ADR exists to fix.
- **JSONB contents blob per Content Item** (ADR-0007's "Deferred" option). Rejected for the same reason ADR-0007 rejected it: complexity today, and the project deliberately chose named paired columns in ADR-0003 to keep the publish gate explicit at the column level.

## Consequences

- **ADR-0003's "third Locale requires extending every table" cost is now paid.** This migration adds paired `*_en` columns to every Content Item table, every per-table trigger, the shared `validate_content_item_publish` function, and the `publish_content_item` RPC's per-table select. The migration is split into two sequential idempotent files:
  - `00000000000013_add_en_locale_columns.sql` — `ALTER TABLE … ADD COLUMN IF NOT EXISTS … EN text NULL` for every paired column on every Content Item table. Safe to run with the existing publish gate; the new columns accept NULL so existing rows are not invalidated.
  - `00000000000014_enforce_en_publish_gate.sql` — `CREATE OR REPLACE FUNCTION validate_content_item_publish(… title_en_in text, body_en_in text …)` requiring non-empty `_en` for `status = 'published'`, the per-table triggers passing the new column values, and `publish_content_item`'s per-table `SELECT` lists gaining the new columns. **Run 014 only after every existing Published Content Item has been backfilled with English text**; until then the old gate remains the safe default. The migration file is written so that running it before backfill will reject publish attempts on rows with empty `_en`; it will not invalidate already-published rows (the gate runs only on `INSERT`/`UPDATE`).
- **A future deprecation of English is approximately symmetric in cost to its addition.** Removing `en` is a paired-column drop plus a gate-narrowing migration.
- **The Portal editor form must render three Locale panes per Content Item.** ADR-0007's rationale that "no casual add" should be possible is preserved by keeping the gate at the schema rather than the UI: even if the Portal is misconfigured to hide the English pane, the database will reject any publish attempt with empty `_en` once 014 has run.
- **`generateStaticParams` and `dynamicParams = false` semantics are unchanged for the new segment.** Each Locale gets its own static render; the i18n type checker enforces that no `Record<LocaleCode, …>` leaves a Locale undefined at compile time.
- **The locale switcher now lists three Locales instead of two.** The pattern is unchanged — each entry is rendered as a `<Link>` to `localePathFor(pathname, targetLocale)` with the active state lifted in gold.
- **Accept-Language detection runs only on the root `/` route.** Once a visitor lands on `/<locale>/…`, the Locale is URL-encoded (per issue 10 of the planning tracker — "the locale encoding lives entirely in the URL, no JS cookies"). The detector does not set a cookie and does not override an explicit Locale segment. The default for an unspecified or unparseable `Accept-Language` remains `ar` (matching `DEFAULT_LOCALE`).
